# dflash

Speculative decoding for GLM-4.6 in llama.cpp on gx10. Target: the `glm46-abl-mtp-IQ2_XXS-Q5K` GGUF from `gguf/`,
which carries the MTP layer as `blk.92`. On Qwen3.5-397B, DFlash on this box raised decode from ~6 to 22 tok/s
(fine-tuned drafter). No public DFlash or EAGLE-3 drafter exists for GLM-4.5/4.6 on Hugging Face (searched 2026-10-03
for eagle, dflash, dspark, speculator and the z-lab, RedHatAI, modal-labs, lmsys and nvidia accounts).

## llama.cpp and the GLM4_MOE target

At `4ebdf2c`, `draft-eagle3` and `draft-dflash` with a GLM4_MOE target abort with
`src/llama-graph.cpp:1384: GGML_ASSERT(t_layer_inp[il] != nullptr && "layer input tensor is null")`: the
`src/models/glm4-moe.cpp` graph does not expose layer inputs. The other 19 graphs (qwen3moe, minimax-m2, deepseek4 and
others) do. The fix is `patches/glm4-moe-layer-inp.patch`, one line at the top of the layer loop:

```
res->t_layer_inp[il] = inpL;
```

With the patch, the input of layer `id+1` matches `l_out-<id>` from `cb_eval` bit for bit (max|diff| 0) on 32 tokens,
with two ubatches of 16 and with two sequences packed into one batch (`tools/hsdump.cpp`, `tools/packtest.cpp`, CPU
build of 4ebdf2c, random model from `test-llama-archs -a glm4moe`). The output of the last layer (`lid = n_layer`)
still aborts: glm4-moe trims the last layer's rows to `inp_out_ids`. A DFlash drafter that reads layer 91 would need a
second change modelled on `mimo2.cpp`; the default SpecForge ids for 92 layers (`[1,23,45,67,89]`) do not.

Plumbing on a random tiny GLM4_MOE (acceptance is zero there, only startup is checked):

| mode | 4ebdf2c | patched |
|---|---|---|
| no speculation, `ngram-mod` | works | works |
| `draft-mtp`, `draft-mtp` + `ngram-mod`, `--spec-synth-len` | works | works |
| `draft-eagle3` | aborts | works |
| `draft-simple` (0.6B draft) | works | works |
| `draft-dflash`, features up to the second-to-last layer | aborts | works |
| `draft-dflash` with a last-layer feature | aborts | aborts |

The patch is applied to `~/llama.cpp` on gx10 and llama-server was rebuilt on 2026-10-03 (together with the `q8_0-q4_0`
FA kernel, see `serve/gx10/README.md`). Draft measurements on the full model are there too: MTP with n-max 1 is best,
11.45 → 17.39 tok/s.

## Ready-made drafts

`scripts/get_drafts_glm46.sh` downloads and converts both external drafts and checks sha256. Both are on gx10 in
`~/models/glm46-drafts/`.

| draft | flags | size | known facts |
|---|---|---|---|
| MTP `blk.92` from the target GGUF | `--spec-type draft-mtp --spec-draft-n-max 1..3` | target weights, ~2.3 GB of Q4_K experts; KV of one layer, 128 MiB at 32k in f16 | PR #26534; GLM-4.5-Air on Strix Halo (unified memory): acceptance 88.5/71.5/62.9%, 1.25/1.24/1.20x at n-max 1/2/3; full GLM-4.5 UD-IQ2_M 1.07x; MTP acceptance is lower on CUDA than on Vulkan (#26750, open) |
| EAGLE-3 `tw_glm47_eagle3_bf16.gguf` | `-md <file> --spec-type draft-eagle3` | 1.2 GB bf16, 594M parameters, draft vocabulary 32000 | trained on GLM-4.7-FP8, max_length 1024; on its own target AL 2.76, 1.69x (8xH200, B=1, temp 0); its d2t lacks `<think>` and tool tokens; on DGX Spark EAGLE-3 slowed gpt-oss-120b to 0.46-0.71x (PR #18039) |
| `GLM-4.5-DRAFT-0.6B-32k-Q4_0.gguf` | `-md <file> --spec-type draft-simple` | 431 MB | Qwen2.5-0.5B with the GLM vocabulary, trained on a general corpus; the author reports 94% acceptance on code refactoring and ~30% in chat, needs temp 0 or top_k 1 |
| n-gram | `--spec-type ngram-mod` | ~16 MB | drafts only on verbatim repeats of 48+ tokens; inflates acceptance on loops |

A model draft (`-md`) and `draft-mtp` cannot load together: the server has one draft context. `ngram-mod` combines
with either. EAGLE-3 conversion: GLM-4.7 and GLM-4.6 share `config.json` and `tokenizer.json` byte for byte (same git
blobs on HF), so `--target-model-dir` points at the GLM-4.6 small files; repeating the conversion at 4ebdf2c gives the
same sha256 `fd5a1288…`.

## Own DFlash for GLM-4.6

Drafter shape per the paper (arXiv 2602.06036v2) and SpecForge: 5 Qwen3 layers, hidden 5120 (equal to the target,
`fc` is built over `n_target_layers × hidden`), 32×128 query heads, 8 KV heads, intermediate 17408, block 16, features
from layers `[1,23,45,67,89]`, embeddings and head shared with the target. That is ~1.73B parameters: 3.2 GiB in bf16,
~1.8 GB in Q8_0, plus the drafter KV over the target n_ctx (5 layers × 4 KiB per token in f16) and a 40 MiB host buffer
per extracted layer at `-b 2048`. `mask_token_id` 151330 (`[MASK]`, its embedding row is non-zero); `vocab_size` 151552.

Training cost is bounded by data. The paper recipe: ~800K prompts with answers generated by the target itself,
6 epochs. On gx10 at 8.5 tok/s that is ~1.1B generated tokens, years; a feature cache of such a corpus for 5 layers is
~77 TB (51,200 bytes per token in bf16). Qwen experience on this box: a drafter trained from scratch on ~2.7K
self-distilled samples did not learn (unseen AL 1.2); the working one was a warm start from the official z-lab
drafter (1 epoch, 2671 answers, ~2.5 h on GB10). There is no official GLM-4.6 drafter to warm-start from. A drafter
trained for a different target gives near-zero acceptance on a modified model (abliterated Qwen3.8-27B with a foreign
DFlash2: AL 1.5, slower than no speculation).

Training features can be captured by llama.cpp itself, without vLLM: `llama_set_embeddings_layer_inp(ctx, lid, true)`
before decode and `llama_get_embeddings_layer_inp(ctx, lid)` after (`src/llama-ext.h:110-115`), with the patch above.
`tools/hsdump.cpp` checks this path on random tokens; real extraction needs token ids and a loss mask read from a file.
